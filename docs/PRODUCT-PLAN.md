# 产品规划：用户离场，工作继续

> 版本：v0.1 · 制定日期：2026-09-17
> 规划窗口：2026-09-17 至 2027-03-16
> 定位：指导产品取舍、阶段验收与开发优先级，不是详细技术设计或交付日期承诺。
> 已确认的是产品目标与原则；首发场景、阶段范围和技术方案仍需在实际开发、使用中验证。

> 当前先执行 [10 天验证冲刺](VALIDATION-SPRINT.md)，用最小 Bot + 云服务链路验证离场价值、用户体感和能力边界。冲刺结果不自动视为阶段一或 V0 达标；完成后依据实测修订本规划并决定是否进入规范开发。

## 1. 产品目标

**把工作台和执行环境迁移到云端，让用户关闭电脑、退出 App 或离开网络后，工作仍能在授权范围内持续推进。**

App 是用户委派工作、观察进度、作出决策和验收结果的窗口，不再是执行必须依附的宿主。

产品应带来三个可验证的结果：

1. **离开设备**：工作不依赖当前电脑在线，执行不占用本机的计算、存储和后台进程资源。客户端自身仍会有正常的显示与网络开销。
2. **释放注意力**：用户不必持续盯日志、补指令和确认普通步骤，只在真正需要决策、处理异常或接收交付时被通知。
3. **减少协调劳动**：逐步减少上下文搬运、询问、催办和结果转交，而不是增加一个需要用户管理的聊天窗口。

“持续推进”不意味着无限运行，也不意味着任何事情都能自动完成。遇到授权、预算、信息或安全边界时，应按约定等待、暂停或升级给用户。

### 1.1 为什么不是 VCoder CLI + skills 的另一个外壳

VCoder 已能提供推理、工具调用、skills 和单任务多 agent 分工。产品不以重复这些能力作为卖点。

用户当然可以自行把 CLI 部署到服务器，再配置进程管理、通知、凭据、存储和恢复。我们提供的价值是：**用户无需自己建设和维护这套环境，就能放心委派、离场和回来验收。**

只有云端计算而没有异步交付，仍可能只是需要远程盯守的终端；只有通知而没有可控执行，也不能让用户放心离开。

### 1.2 多 bot 是手段，不是目标

不预设必须有多个 bot，不以 bot 数量衡量进展。

优先使用单 bot + VCoder + skills/子 agent 完成真实工作。只有实际场景证明需要独立的服务对象、授权、信息边界或责任主体时，才验证多 bot 协作。

研究、编码、测试等任务拆分默认属于执行内核，不自动对应独立 bot。多 bot 不列为半年必交付项。

## 2. 首发用户与场景假设

### 2.1 首发用户

优先验证已经使用 VCoder、有明确可验收任务的个人开发者。个人用户也能获得设备和注意力解放，团队协作不是产品成立的前提。

在个人闭环成立后，再选择具有真实交接需求的小型团队验证协调收益。首发用户选择是范围控制假设，不是将产品永久限定为研发工具。

### 2.2 首个完整场景

建议以“离开电脑后完成指定仓库的一项有限变更”为首个端到端场景：

1. 用户连接仓库，说明目标与验收条件，限定可操作范围和预算。
2. 云端准备工作空间，接收并持久化任务；客户端显示已接收后，用户可以关闭电脑。
3. VCoder 在云端调查、修改、测试，保存产物和执行证据。
4. 若遇到需要决策的问题，系统发出明确通知；没有回复时不擅自扩大权限。
5. 用户从另一台设备查看进度、回答问题，或停止任务。
6. 最终交付变更、测试结果、已知问题和下一步选项。推送、创建 PR 等对外动作必须有明确授权。

首个场景不要求多个 bot，不要求自动发布，也不要求用户持续观察 token 流。

### 2.3 后续候选场景

- 定时完成资料或仓库巡检，只有有意义的变化才通知用户。
- 等待外部信息后继续原任务，而非要求用户重开会话、重述背景。
- 经授权联系相关参与者、收集反馈、推动一项事项完成。

每次只增加能验证新用户收益的场景，不同时铺开大量工具和业务领域。

## 3. 核心体验与产品约定

### 3.1 委派一次

任务至少能表达：目标、交付物、输入材料、验收条件、允许的操作、资源预算，以及遇到阻塞后的处理方式。

不把委派变成长配置表。常用范围可通过默认值或模板提供；高风险授权必须明确展示，不能隐藏在模板中。

### 3.2 离场后继续

- 客户端断开不会取消、暂停或遗失已确认接收的任务。
- 任务不能暗中依赖用户本机的工作目录、浏览器或 MCP 进程。
- 需要本地文件时，先完成经用户同意的上传或同步，再确认任务具备离线执行条件。
- 云端服务本身也可能故障；必须展示真实状态并支持恢复，不能承诺永不中断。

### 3.3 必要时再打扰

默认围绕三类事件通知：需要用户决策、需要用户处理的异常、交付就绪。

决策通知应说明：为什么受阻、有哪些选择、推荐方案、影响和不回复时的行为。低价值进度更新合并为摘要，不为每个工具调用发送通知。

### 3.4 随时观察、干预和接管

用户可以在不恢复原客户端连接的情况下，查看当前状态、剩余阻塞、已有产物、用量和授权，并暂停、取消或撤销后续授权。

取消不等于回滚已经发生的外部副作用；界面应区分“已请求取消”“执行已停止”和“已有操作不可撤销”。

### 3.5 回来可以验收

交付包括结果、证据、失败或未验证事项，而不只是“已完成”的模型回复。执行结束与用户验收通过是不同状态。

## 4. 技术分工与开发原则

```text
App / Web / 其他访问入口
  委派 · 状态 · 通知 · 审批 · 停止 · 验收
                    │
                    ▼
vcoder-bot：云端工作控制层
  身份与授权 · 任务与状态 · 调度 · 产物 · 审计
                    │
                    ▼
VCoder：共享执行内核
  推理 · skills · 工具 · 上下文 · 单任务多 agent
                    │
                    ▼
受控云端工作环境
  工作目录 · 文件 · 进程 · 浏览器 · 网络 · 临时凭据
```

### 4.1 复用与边界

- VCoder 是主执行内核，不另造重复的推理或子 agent 框架。
- vcoder-bot 管理跨客户端连接、跨执行尝试的工作生命周期。
- 身份、任务、一次执行尝试和推理会话分开建模，不能把聊天记录作为唯一事实来源。
- 云端任务状态和审批应独立于运行时内存存在；历史续聊不等于执行现场恢复。
- 本地 Docker 用于开发和验证，不等于最终云端产品；原 Grok Bot 拓扑也不构成未来设计约束。
- 具体数据库、队列、云厂商和隔离粒度由阶段技术设计决定，不在产品文档中提前锁死。

### 4.2 当前能力如何看待

前期只读调查表明，两个仓库已有进程内 VCoder runtime 接入、流式响应、bot 状态与记忆、消息链路、box 执行以及部分调度和历史持久化基础。但这不是云端产品的端到端验收结论。

必须重新验证的边界包括：客户端退出后的服务生命周期、重启恢复、待审批状态、可靠通知、外部操作重复执行，以及当前 UI 与宿主的耦合。

现有研究文档 [CURSOR-TECHNICAL-OVERVIEW.md](CURSOR-TECHNICAL-OVERVIEW.md) 是历史技术调查参考，其中接入建议可能已落后于当前实现。它不是本产品的功能清单或架构约束，开发以当前源码和实测为准。

### 4.3 安全从第一次云端执行开始

- 首次远程使用即需要认证、任务访问控制、传输保护、受限工作空间和最小权限凭据。
- 不默认上传整套本地认证目录；明确用户上传的数据、用途、保留与删除方式。
- 云端凭据按任务或工作空间授权，日志、通知和模型上下文不得泄露密钥。
- 上传第三方代码、使用上游 renderer/素材、对外发布前分别确认数据授权和素材使用权。
- 网络访问、命令执行和不可信仓库内容属于安全边界，不能仅靠 prompt 限制。
- 对外发消息、推送、发布、删除等操作必须符合预先授权或单次审批。
- 不承诺所有操作恰好执行一次。对可重试操作做幂等控制；结果未知的高风险操作先核查或请求人工处理。

## 5. 半年路线图

每阶段以用户结果作为门槛。日期是规划窗口，不是对开发耗时的预测；若关键验收未通过，应延后扩展而不是跳过基础问题。

### 阶段一：证明“可以关掉电脑”

**窗口：2026-09-17 — 2026-10-16**

交付重点：

- 打通一条不依赖用户本机存活的云端 VCoder 执行链。
- 支持一个用户、一个云端工作空间和一种有限仓库任务。
- 云端保存任务接收记录、状态、产物和必要执行记录。
- 客户端可以重连查看；提供最小远程身份认证、权限、资源限额和停止能力。
- 明确本地输入的上传边界及云端凭据配置方式。

验收门槛：

- 云端确认接收任务后，关闭发起电脑，任务仍能执行并保存交付物。
- 用户从另一设备登录后能查看相同任务，无需重发 prompt。
- 验证执行未回落到用户本机；客户端断线不会触发任务取消。
- 未授权访问被拒绝，凭据不出现在产物或日志中。

不做：多 bot、通用插件市场、复杂团队管理。

### 阶段二：证明“可以不盯着”

**窗口：2026-10-17 — 2026-11-16**

交付重点：

- 固化目标、验收、授权、预算与阻塞处理的委派体验。
- 提供一个可在桌面 App 关闭后到达用户的通知渠道。
- 提供轻量跨设备查看和审批入口；不强制先开发原生移动 App。
- 区分待执行、执行中、待决策、交付就绪、失败与取消等用户可理解的状态。
- 交付结果摘要与证据，不要求用户阅读全量日志。

验收门槛：

- 在固定场景中，用户离场后普通步骤无需逐项确认。
- 真正阻塞时只发出必要且可操作的通知；不回复不会导致越权推进。
- 审批与原任务对应，重复点击不会重复执行，过期或撤销授权不再生效。
- 与本地 VCoder + skills 基线比较人工介入次数和主动查看次数。

不做：用减少必要安全确认的方式制造“无人值守”效果。

### 阶段三：证明“中断后仍然可信”

**窗口：2026-11-17 — 2026-12-16**

交付重点：

- 完善任务与执行尝试的持久化状态、心跳、失联识别及恢复规则。
- 处理执行失败、连接中断、进程重启、凭据失效和通知失败。
- 建立外部操作记录、重复请求保护、待审批恢复与事件回放。
- 支持备份恢复和产物保留策略。

验收门槛：

- 对“执行前、执行中、外部操作已发生但结果未保存”等位置注入故障。
- 恢复后不丢失已接收任务，不将未知结果标为成功，不盲目重做高风险操作。
- 用户能看清哪些工作已完成、哪些待核查、哪些可以继续。
- 通知失败可查、可重试，不导致任务状态消失。

阶段一已有的最小可靠性不能等到本阶段才建立；本阶段扩展故障覆盖并系统化验证。

### 阶段四：证明“长期职责无需重复布置”

**窗口：2026-12-17 — 2027-01-16**

交付重点：

- 在一次性任务闭环上增加一个定时或事件驱动的真实场景。
- 调度独立于客户端和推理会话；明确停机错过触发后的处理规则。
- 保存职责配置、历史交付与有来源的必要记忆，允许修改和删除。
- 支持等待用户或外部信息后继续工作，避免反复重建上下文。
- 增加事件去重、通知合并、循环限制与任务预算。

验收门槛：

- 用户只配置一次，后续触发不依赖本机在线。
- 没有值得报告的变化时不制造噪声；触发风暴不会无限创建任务。
- 暂停职责后不再触发新工作，已有执行的处置清楚可见。
- 不把过期记忆当作当前事实，结果仍需引用实际证据。

不做：为了演示自治而主动扩张任务范围。

### 阶段五：验证“减少协调劳动”

**窗口：2027-01-17 — 2027-02-16**

交付重点：

- 选择一个真实交接流程，例如收集问题信息、等待负责人决策并返回结果。
- 明确参与者身份、谁可以决策、哪些信息可以共享、对外联系的授权范围。
- 让参与者能够补充、查询和接管事项，不依赖发起者转述。
- 先用单 bot + skills/子 agent 验证；出现独立权限或责任边界时，才开展多 bot 对照实验。

验收门槛：

- 相比用户手动转发与催办，信息搬运和跟进次数减少。
- 责任、决策来源和下一步明确，不产生无人接手的“已发送”消息。
- 如试验多 bot，必须证明它相对单 bot 的收益，并计入成本、延迟、故障和维护负担。
- 若无收益，保留单 bot，不以完成多 bot 架构作为验收条件。

条件分支：若尚无可信的协调场景，继续强化个人异步工作闭环，不为满足月份安排虚构团队需求。

### 阶段六：受控试点与产品收敛

**窗口：2027-02-17 — 2027-03-16**

交付重点：

- 在真实任务中持续试用，覆盖首次配置、委派、离场、审批、验收和故障处理。
- 收敛自有可维护界面，解除核心体验对上游封闭 renderer 的依赖；相关素材权利在任何外部分发前确认。
- 完善数据导出与删除、预算、云端资源休眠回收、升级与恢复流程。
- 固化基准任务集、失败案例和人工介入分类。
- 依据证据决定下一阶段扩大场景、开放用户还是继续修复核心闭环。

验收门槛：

- 连续跨天使用不要求用户保持电脑在线，也不要求持续查看过程。
- 结果有证据，失败可解释，操作可审计，费用与资源上限可理解。
- 用户能从另一设备停止工作、处理阻塞并验收交付。
- 已知安全和可靠性问题有明确处置；存在阻断性问题时不扩大试点。

## 6. 如何衡量成功

先建立固定任务集和本地 VCoder + skills 基线，再记录每阶段变化。第一阶段确定样本与数值目标，未经试用不预填漂亮但无依据的成功率。

| 指标 | 定义与用途 |
| --- | --- |
| 离场交付率 | 已确认接收且约定输入齐备的任务中，发起设备离线后仍产生可验收交付的比例 |
| 人工介入次数 | 从委派到交付的补指令、解除阻塞、重述背景次数；必要审批单独统计 |
| 主动查看次数 | 用户因不确定状态而主动打开界面的次数；试点结合访谈区分正常查看与焦虑盯守 |
| 验收通过率 | 用户或约定测试接受交付的比例，不以模型的完成声明代替 |
| 恢复结果 | 故障注入与实际故障后，安全恢复、明确暂停或遗失/误执行的分类统计 |
| 通知有效性 | 需要行动的通知是否到达、是否可操作，以及重复或无意义通知数量 |
| 协调劳动 | 同一流程需要用户转发、催办、复述和人工交接的次数 |
| 单次有效交付成本 | 模型、云端执行、存储等可计量成本；无法统计的部分明确标注 |
| 安全底线 | 越权、凭据泄露、重复高风险副作用、无法停止等事件与处置记录 |

安全底线不能用平均收益抵消。多 bot 若增加成本与注意力负担而未改善验收结果，就不采用。

## 7. 半年内不预先承诺的范围

- 必须实现多 bot、bot 自主组队或复杂组织结构。
- 重写 VCoder 执行内核，或把支持更多 provider 当作核心目标。
- 通用企业 SaaS、多租户计费和大规模集群调度。
- 所有桌面与移动平台同时提供完整原生客户端。
- 通用市场、大量第三方业务连接器。
- 不受限的自动发布、对外承诺或生产运维。
- 完整复刻原 Grok Bot / Cursor 的产品与协议。

排除这些范围不代表忽略基本安全：一旦开放给多个用户，就必须满足相应隔离与访问控制要求。

## 8. 主要风险与待验证决策

| 风险或问题 | 开发指导 |
| --- | --- |
| 只是把终端搬到云端，仍需盯守 | 用人工介入、通知质量和交付体验验证，不只展示远程执行成功 |
| 本地工具、文件或登录态导致隐藏依赖 | 每个场景做“发起设备关机”测试，明确上传和云端替代方案 |
| 云端常驻成本过高 | 分离持久职责与活跃计算；等待不应等于持续占用高配机器 |
| 不可信代码或网页诱导越权 | 授权由系统执行，限制网络、工具和凭据，不信任内容中的指令 |
| 自动重试造成重复外部操作 | 记录操作状态，核查不确定结果，对高风险动作保守恢复 |
| 云端代码与数据不被用户接受 | 明确托管边界、保留政策和删除能力；验证是否需要私有部署 |
| 旧 UI、协议与新生命周期强耦合 | 原实现作为参考，逐步建立自有访问入口和控制接口 |
| 基础设施建设吞掉产品验证 | 每阶段交付一个用户可体验的闭环，而非仅完成底层模块 |

启动阶段需要确定：首个试点任务、云端部署形态与费用承担、仓库/凭据接入方式、首个离线通知渠道、跨设备入口以及数据保留政策。这些决定进入对应技术方案，不用未经确认的默认选择替代。

## 9. 开发决策与文档维护

每项开发工作在开始前回答：

1. 改善“离开设备、释放注意力、减少协调劳动”中的哪一项？
2. 为什么不是直接复用 VCoder 或一个 skill 就能满足？若能复用，新增工作是否只在必要的产品层？
3. 对应哪个真实场景，如何验收，失败时用户会看到什么？
4. 是否引入新的数据上传、授权、持续费用或不可逆副作用？
5. 能否用更简单的实现先验证？

任务描述应记录用户结果、验收方法、非目标和风险。详细接口、迁移与故障处理写入各阶段技术设计，不把未经验证的技术选择升级成产品前提。

本文件是后续产品取舍的依据，不自动授权破坏性迁移、生产部署、外部发布或凭据上传。历史研究文档与本规划冲突时，产品方向以本规划为准；源码实际状态以重新核查为准。

每阶段复盘时更新假设与范围，保留变更原因。未通过验收则调整后续窗口；无法证明独立用户价值时，停止扩大独立产品范围，优先将有用能力回归 VCoder。
