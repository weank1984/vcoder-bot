## 1. 目标

在 10 天内用一条真实、可重复验证的端到端链路回答三个问题：

1. **链路是否成立**：云端确认接收任务后，发起设备断网或关闭，任务仍能继续并保存交付物；用户可从另一设备查看和取回结果。
2. **用户体感是否成立**：用户知道何时可以离开，不需要盯日志，回来后能理解状态、失败原因和交付证据。
3. **方案边界在哪里**：用实测说明支持的任务、仓库、执行时长、资源、网络、并发及恢复边界，避免凭单次成功演示推断产品能力。

本冲刺是规范开发前的产品与技术验证，不是 V0、V1 或生产发布。允许使用单节点和有限可靠性实现，但必须如实展示限制，不能用界面文案把未实现能力包装成已具备能力。

## 2. 核心假设与判定

| 编号 | 假设 | 主要证据 | 冲刺通过参考线 |
| --- | --- | --- | --- |
| H1 | 工作可以脱离发起设备继续 | 发起设备离线任务集、跨设备取回记录 | 所有已确认接收的离线用例均不因客户端断开而中止 |
| H2 | 云端链路自身足够稳定 | 接收、启动、执行、保存、下载各阶段事件 | 基础设施链路成功率 ≥ 90%，失败均有明确阶段和原因 |
| H3 | 结果质量不因迁移云端明显恶化 | 同仓库、同模型、同任务的本地 VCoder 对照 | 分别报告验收率和差异，不用链路成功代替结果正确 |
| H4 | 用户可以不盯日志 | 用户试用记录、主动查看和补指令次数 | 信息齐备任务中多数无需中途补指令；用户能在 1 分钟内找到状态和交付证据 |
| H5 | 成本和能力边界可测 | 每任务时长、token/请求、资源和失败分类 | 每项数据可追踪，未知项明确标记，不按零处理 |

参考线用于判断是否值得继续，不是对外 SLA。样本不足时保留原始数字和置信限制，不为通过而删除失败样本。

## 3. 验证范围

### 3.1 必须具备

- 单个试点身份、一个云环境、全局并发 1；有余量时再测试并发 2。
- 一种 Git 仓库输入：仓库 URL、分支和固定 commit；首轮使用无需凭据的测试仓库，随后验证一个只读私有仓库。
- 目标、验收条件、允许操作、执行上限随任务一起持久保存，并返回稳定 `taskId`。
- 云端 worker 在独立 workspace 中运行 VCoder，允许在 workspace 内修改文件和执行测试。
- 提交、任务列表、任务详情、停止请求及交付下载的最小 Web 入口，桌面和移动浏览器均可使用。
- 至少区分：`accepted`、`preparing`、`running`、`stopping`、`delivered`、`failed`、`cancelled`、`interrupted`。
- 交付至少包含：输入 commit、变更摘要、patch、修改文件清单、测试命令与输出、未验证事项、用量和执行时长。
- 强制墙钟超时、VCoder 最大轮次、输出大小限制和执行容器终止；达到限制后保留已有产物。
- 服务进程重启后任务记录和已有产物仍可查询。执行中任务可诚实标记为 `failed` 或 `interrupted` 后手动重试，不承诺恢复任意进程现场。
- 事件记录贯通 `taskId`、`runId`、阶段、时间和错误分类；不得记录密钥。

### 3.2 明确不做

- 多租户、组织角色、团队共享和大规模并发。
- 多 bot、自主组队、定时职责或通用插件市场。
- 完整审批状态机、通知送达保证和自动恢复执行现场。
- Kubernetes、跨区域部署、自动扩缩容或正式灾难恢复。
- 自动 push、创建 PR、发布、删除远程资源、对外发消息等副作用。
- 恢复或复刻完整 Electron 工作台；验证入口采用独立轻量 Web。
- 宣称通过 [PRODUCT-SPEC.md](PRODUCT-SPEC.md) 的 V0/V1/V2 或 A01—A14 全量门槛。

## 4. 默认实现方案

默认方案以最快获得可信证据为目标；实测证明不适用时记录原因再调整。

```text
浏览器
  提交 · 状态 · 停止 · 交付下载
                    │
                    ▼
单节点验证服务
  HTTP API · 身份令牌 · 任务/事件存储 · worker 调度
             │                       │
             ▼                       ▼
       持久化数据目录           单任务执行环境
       任务 · 事件 · 产物       Git 快照 · VCoder · 测试
```

| 决策 | 冲刺默认值 | 选择原因与限制 |
| --- | --- | --- |
| 部署 | 一台 Linux 云主机，Docker Compose 或等价单机部署 | 验证客户端离场和云端执行，不验证集群调度 |
| 服务 | 一个 Node.js 服务同时提供 API、静态 Web 和单 worker 调度 | 减少分布式组件；服务重启时运行中任务不自动恢复 |
| 持久化 | SQLite WAL + 本机持久盘；产物存文件目录 | 足够支撑单节点验证；规范开发再评估数据库和对象存储 |
| 身份 | 单个高熵访问令牌，所有 API 服务端校验 | 不是正式账号系统；令牌不得进入 URL、日志或通知 |
| 仓库 | 首轮公开仓库；私有仓库使用单独的只读、短期凭据 | 不上传本机 Git/SSH 配置，不允许 push |
| VCoder | 独立 Docker runner 内运行 `@vcoder/server` runtime | 复用现有执行内核；控制面不加载模型凭据或不可信仓库代码 |
| 工作区 | 每个 Run 使用独立目录；输入固定到 commit | 重试创建新 Run，不覆盖前次记录 |
| 停止 | 持久保存停止请求，再取消 runtime；必要时终止执行进程/容器 | 界面区分“正在停止”和“已停止” |
| 状态更新 | 页面轮询带版本的任务快照；事件用于诊断和后续演进 | 冲刺不要求 WebSocket/SSE |
| 通知 | Day 7 后按余量接一个 webhook/邮件渠道 | 不阻塞 H1；未接入时不声称支持离线通知 |
| 数据保留 | 验证数据默认保留 7 天，可手动删除活动数据 | 仅限受控试验，不能扩展到外部试点 |

### 4.1 首发执行模板

- Linux amd64、Node.js/TypeScript 仓库；无 GUI、GPU、嵌套虚拟化要求。
- 初始单任务上限：30 分钟、VCoder 16 轮、2 GiB 输出/产物目录、10 MiB 单个下载文件。
- 初始执行资源目标：2 vCPU、4 GiB 内存、10 GiB workspace；能否强制取决于实际部署方式，未强制的值必须显示为“目标”而不是“硬限制”。
- 网络默认只允许 Git 获取、所选模型 provider 及任务声明的依赖源。若冲刺环境暂不能实施出口白名单，任务详情必须展示这一限制，且不得使用生产或高价值凭据。
- VCoder 的文件修改和测试命令仅在隔离 workspace 内预授权。读取宿主目录、云元数据、控制面数据和注入的秘密始终禁止。

## 5. 最小用户旅程

1. 用户打开验证入口并通过访问令牌认证。
2. 用户填写仓库、commit、目标、验收条件和执行上限。
3. 服务完成参数校验和持久化，返回稳定 `taskId`。
4. 页面显示“云端已接收，可以关闭此设备”；只有到达 `accepted` 后才能显示该文案。
5. worker 准备 workspace、运行 VCoder、执行或收集测试并持续更新阶段。
6. 用户可关闭发起设备，并从另一浏览器查看同一任务；不要求重发 prompt。
7. 用户可请求停止。服务先显示 `stopping`，实际执行结束后才进入 `cancelled`。
8. 任务结束后，用户在第一屏看到结果摘要、测试结论、未验证事项、用量和下载入口，不需要阅读全量日志。

## 6. 数据与安全边界

- 不接受整套本机 `~/.vcoder`、`~/.codex`、`~/.claude`、SSH 或浏览器目录上传。
- 模型凭据只通过云环境 secret 注入，不写入任务 JSON、事件、产物、prompt 或页面。
- 私有仓库凭据必须只读、可撤销、短期使用；clone 后不得把带凭据 remote URL 写入交付。
- worker 不获得 push、PR、发布或云控制面管理权限。
- API、任务、事件和下载均校验同一个服务端访问令牌；即使单用户也不能提供未鉴权下载链接。
- 日志和交付完成后执行密钥模式扫描；发现疑似密钥即判定该任务验证失败并停止扩大试用。
- 未实现的网络隔离、资源硬限制、备份与删除保证必须列入已知限制，不用 prompt 约束代替系统约束。

## 7. 事件、交付与测量

### 7.1 最小事件

| 事件 | 必要字段 |
| --- | --- |
| `task.accepted` | taskId、input commit、limits、acceptedAt |
| `run.started` | taskId、runId、worker/version、startedAt |
| `run.stage_changed` | runId、from、to、occurredAt |
| `run.usage_updated` | runId、模型请求、input/output token；未知值保留未知 |
| `stop.requested` | taskId、runId、requestedAt |
| `run.finished` | runId、outcome、duration、errorClass |
| `artifact.created` | taskId、runId、kind、path、size、sha256 |

### 7.2 交付包

- `summary.md`：目标对照、改动、测试、未验证事项和已知限制。
- `changes.patch`：相对于输入 commit 的 patch。
- `files.json`：修改文件和基本统计。
- `tests.json` 与 `test-output.txt`：命令、退出码、耗时和截断说明。
- `usage.json`：模型用量、墙钟时间和资源信息；不可测值标记为 `unknown`。
- `events.jsonl`：经过脱敏的任务事件，用于链路与故障分析。

### 7.3 统计口径

- **基础设施链路成功**：任务被唯一接收，worker 启动，结果状态被保存，用户能够查询和下载；不代表代码正确。
- **结果验收通过**：用户验收条件或预定测试接受交付；模型自述不算证据。
- **人工介入**：提交后补充指令、解除非预设阻塞、重述背景的次数；停止和预设安全决策单列。
- **主动查看**：用户因不确定而打开详情的次数；通知跳转和最终验收不算焦虑查看。
- **离场用例**：服务确认 `accepted` 后关闭或断开发起设备，另一设备完成查询和取回。

## 8. 任务集与边界实验

建立 12—20 个任务，保留所有失败和主动放弃样本：

| 类别 | 需要覆盖 |
| --- | --- |
| 正常任务 | 小型代码修改、测试修复、纯调查、文档或配置修改 |
| 输入问题 | commit 不存在、目标含糊、验收条件矛盾、仓库不可访问 |
| 环境问题 | 缺少工具链、依赖安装失败、测试超时、磁盘或输出接近上限 |
| 中断问题 | 浏览器断开、API 重启、worker 终止、模型限流或失败 |
| 安全问题 | 仓库文本要求读取密钥、访问宿主路径、访问云元数据、尝试 push |
| 规模问题 | 小/中型仓库、5/15/30 分钟任务、并发 1/2、较大测试输出 |

最终边界报告至少回答：

- 可接受的仓库大小、clone/准备时间及主要影响因素。
- 稳定任务时长、最大验证时长和超时后的产物完整度。
- 模型请求、token 和云资源成本分布。
- 支持与不支持的语言、工具链、网络和认证方式。
- worker/API 重启时哪些状态可恢复、哪些必须人工重试。
- 并发增加时出现的排队、资源和状态一致性问题。
- 用户最常困惑、最常主动查看或最需要补指令的位置。

2026-09-18 按用户指定的 DeepSeek provider 和本机 Docker 路径执行 B01。`deepseek-v4.1-flash` 被 API 明确拒绝，受权模型列表只提供 `deepseek-flash` 与 `deepseek-v4-pro`，因此实际验证采用 `deepseek-flash`。完整原始记录见 [validation-evidence/2026-09-18-b01-deepseek-local-docker.json](validation-evidence/2026-09-18-b01-deepseek-local-docker.json)：

- 前四次尝试分别暴露 Git LFS 缺失、未等待 `session_complete`、早拒绝 Promise 竞态/模型 ID 不兼容、受限 Bash 无法运行验收命令；所有样本均保留，没有从成功率分母中删除。

- 未跟踪新文件现会进入 `changes.patch`；只有声明 `test` 的任务能执行精确的独立命令 `git diff --check`，任何复合命令、替代 cwd 或其他 Bash 命令仍拒绝。
- 修复后 r5/r6 两次均在约 14 秒内交付并通过独立验收；token 分别为 1,658/886 与 1,236/752（input/output），下载哈希与记录一致，workspace 和产物未发现注入密钥。

- 本结果只证明本机控制面 → Docker runner → DeepSeek → 交付下载闭环，不证明 Linux 云主机、跨物理设备离场或用户体感。

## 11. 退出条件与后续决策

冲刺结束只作以下三种判断：

1. **继续规范开发**：H1 成立，链路可靠性和用户体感达到参考线，没有不可接受的安全或成本信号。
2. **调整后再验证**：价值信号存在，但执行内核、交付形态、成本或用户旅程存在可修复阻塞；明确下一轮只验证哪个变化。
3. **停止独立产品化**：无法证明离场价值，或相较本地 VCoder 没有减少注意力和运维负担；可复用能力回归 VCoder。

继续规范开发时，先根据实测修订 [PRODUCT-PLAN.md](PRODUCT-PLAN.md) 和 [PRODUCT-SPEC.md](PRODUCT-SPEC.md)，再确定正式控制面、隔离、身份、通知、恢复和数据政策。验证代码默认视为原型；只有通过设计评审、补齐测试和迁移方案的部分才进入正式架构。
